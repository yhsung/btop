# P2 btop-menu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `btop-menu` crate: transcribed tables, owned options state machine, msgBox, all 7 menus + dispatcher, with overlay byte parity and P1-`Action` side effects.

**Architecture:** New workspace member `btop-menu` (zero third-party deps; path deps on `btop-input` for `Action`, `btop-config`, `btop-draw` for createBox/banner/ansi). Menu logic is pure over explicit inputs (`MenuState`, option stores); all mutations emit `Action`s for the P3 sink. Overlay strings byte-compare against extended `draw_golden` fixtures.

**Tech Stack:** Rust 2021, `cargo test`, C++ harness extension via CMake `BUILD_TESTING=ON`.

**Spec:** `docs/superpowers/specs/2026-09-06-menu-p2-design.md`

## Global Constraints

- Zero third-party dependencies (path deps on workspace crates only).
- `cargo test --workspace --locked --offline`, `cargo clippy --workspace -- -D warnings`, `cargo fmt --check` green after every task.
- Transcribe tables/branches verbatim from cited `src/btop_menu.cpp` lines; deviations need a comment + report.
- `poll`/`wait`/fd/terminal syscalls are NOT ported (P4 scope). No Runner execution (P3 sink runs `Action`s).
- Every new `Action` variant must have ≥1 construction site (test or impl) — no `#[allow(dead_code)]` reintroduced.
